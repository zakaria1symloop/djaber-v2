# 04 — AI pipeline

Module `ai` (+ `agents`, `messaging`). Vercel AI SDK (`ai` package, `generateText` with `tools` and `experimental_output` / `generateObject` for structured output) over provider packages `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/google`, `@ai-sdk/groq`. All thresholds below are constants in `apps/api/src/modules/ai/ai.constants.ts`.

---

## 1. Ingestion → eligibility (messaging module, FL-01 steps 1–9)

`InboundProcessor.process(inboundEventId)`:

1. Parse the Meta entry (05-integrations §1.3). Ignore: `is_echo`, `read`, `delivery`, `reaction`, events without `message` or `postback`.
2. `Channel` by `(platform, externalId=recipient.id)`; status not `active` ⇒ stop (log `channel_inactive`).
3. `Conversation` find-or-create `(channelId, externalSenderId=sender.id)`; `Client` via `ClientIdentity(channelId, externalSenderId)` else create placeholder `Client{ name: 'FB User ·'+last6 | 'IG User ·'+last6, isPlaceholder: true, source: 'ai' }` and fetch profile once (`GET /<psid>?fields=first_name,last_name,profile_pic` with page token; failure ⇒ keep placeholder).
4. Insert `Message{ direction:'in', author:'customer', externalId: mid, text, attachments:[{type,url,mime?}], payload:{ postback?, quickReply?, stickerId? } }`; `U(conversationId, externalId)` violation ⇒ stop silently (MSG-03). Enqueue `media.fetch-attachment` per attachment. `unreadCount++`, `lastCustomerMessageAt=now`, `lastMessageAt`, `lastMessagePreview`; status `resolved|archived` ⇒ `active`. Outbox `ws:message.created`.
5. Blocked customer (`CustomerBlock` for this client or platform blacklist by phone) ⇒ stop (stored for evidence, no notification, no AI).
6. Eligibility (04 §5): `needs_human` or `aiPaused` ⇒ F-1 (`conversation.needs_human_message` throttled) and stop. No agent linked (`AgentChannel`) or agent not `active` ⇒ stop.
7. Attachment gates: audio and `agent.voiceTranscription=false` ⇒ system message `unsupportedMedia` (once/24 h) and stop; images and `agent.imageRecognition=false` ⇒ drop images, continue if text else `unsupportedMedia`; video/file/location/sticker only ⇒ `unsupportedMedia`.
8. Credit gate: `plannedCost = max(1, hasAudio?3:0, hasImage?5:0)`; `CreditService.balance(ws) < plannedCost` or monthly conversation quota exceeded (first inbound of a conversation in the period counts) ⇒ F-4: system message `unavailable` (once/24 h), `needs_human`, `credits.exhausted` (1/day) and stop.
9. Blocked words on inbound: mark `Message.flags=['blocked_word']` (does not stop the AI; used by reports).
10. Typing indicator `sender_action=typing_on` (fire-and-forget, 5 s timeout).
11. `BatchingService.schedule(conversationId)`: window = `agent.responseDelaySec` (default 3; UI 0–10); abuse guard: inbound count in 60 s ≥ 20 ⇒ window 10 s; in 10 min ≥ 50 ⇒ handoff (`handoff` system message once, `needs_human`, insight `handoff` detail `abuse_guard`) and stop. Existing delayed `ai-reply` job for the conversation ⇒ `changeDelay` so all messages are answered together.

## 2. Conversation state

`Conversation.context` JSON (versioned, `schemaVersion: 1`):
```ts
type ConversationContext = {
  schemaVersion: 1;
  lastLanguage?: 'ar' | 'arabizi' | 'fr' | 'en' | 'mixed';     // detected from the last customer message (§3.6)
  cart?: { items: { productId: string; variantId?: string; quantity: number }[]; recapShownAt?: string; orderId?: string; updatedAt: string };
  collected?: { name?: string; phone?: string; wilayaId?: number; communeId?: number; communeText?: string; address?: string; isStopdesk?: boolean; stopdeskId?: string };
  lastProductIds?: string[];                                     // ≤ 10, most recent first (used for retrieval context)
  handoff?: { at: string; reason: string; messageSent: boolean };  // one handoff message per episode
  // workspace system messages (R-G keys of `Workspace.systemMessages`) + the 3 fixed platform texts of 11 §9, tracked the same way (once per conversation per 24 h)
  systemMessageSentAt?: Partial<Record<'handoff'|'out_of_hours'|'out_of_stock'|'welcome'|'unavailable'|'unsupportedMedia'|'voiceFailed', string>>;
  unclearStreak?: number;                                        // 3 ⇒ handoff rule "3 messages incompréhensibles"
};
```
Full-test 15/11 AI-CHAT-05 (proposal 6): `chosen?: { productId, variantId | null, quantity | null }[]` — the product(s) the customer chose for the order being taken, from the reply output's `cart` (an empty or missing `cart` never erases it; a placed order clears it). The order section prints it as `CURRENT ORDER (chosen by the customer — keep it …): 2 × Robe satin (M) [VID:…] [ID:…]` (ids outside the turn's catalogue slice are skipped; the chosen ids are added to the slice), like KNOWN CUSTOMER, so a name-only message can no longer make the model ask the product again. Journey retest R1-2 (17/11): a chosen item without a quantity is printed `1 ×` (« a product named without a number counts 1 ») — the old `? ×` (« quantity still to ask ») made the model ask « combien ? » on every turn until the flow died; the order section gives the darija / arabizi numbers (wa7ed / wahda = 1, zoudj / jouj / زوج / جوج = 2, tlata = 3, rab3a = 4…) and asks the quantity only for « des / chwiya / plusieurs ». The playground keeps it on the session's last run that did not fail (`AiRun.meta.chosen`; a run closed `error` is skipped, journey retest R1-1). While it is set, a message that is only an order field is not offered `handoff_to_human` (§4.2) and gets 2 tool rounds at most.
Cart is cleared on `create_order` or 7 days after `recapShownAt` (abandon KPI reads carts with `recapShownAt` in period and no `orderId`). Context updates are written with the conversation `version` increment inside the run's transaction.

## 3. Prompt assembly (`PromptBuilder.build(ctx) → { system, messages, tools }`)

Full-test 15/11 proposal 13 (18 255 input tokens for one turn of a 10-product shop): `BuiltPrompt.cachePrefix` = the sections up to the catalogue (identity, policies, owner instructions, FAQ, catalogue — the same from one turn to the next). The live gateway sends it to Anthropic as a first system block with `cache_control: ephemeral` (≥ ~1 000 tokens; the rest of the system prompt as a second block), so the next turns of a conversation read it from the provider's cache. Other providers get the plain `system` string. The full-catalogue header also says « a product listed here needs no search_products call ».

Sections in this exact order; each section is a function in `prompt/sections/*.ts` and is unit-tested with a snapshot. Language of the prompt itself: English (model-facing); customer-facing strings come verbatim from `Workspace.systemMessages` (keys `handoff`, `out_of_hours`, `out_of_stock`, `welcome` × `fr|ar|en`, R-G) and from the `Agent` columns. `lang` below = the locale picked by §3.6 from `context.lastLanguage`.

1. **Identity & personality** — `You are "{agent.name}", the sales assistant of "{workspace.name}". Personality: {personality}` with the four V1 personality blocks (professional / friendly / casual / technical) stored in `prompt/personalities.ts`.
2. **Shop policies** (agent knowledge step 2): `DELIVERY:`, `PAYMENT:`, `RETURNS:`, `HOURS:` from `Agent.policies { delivery, payment, returns, hours }` (each ≤ 500 chars; empty ⇒ section omitted). Out-of-hours: if `agent.businessHours` is set and `now` (Africa/Algiers) is outside it ⇒ append `OUT_OF_HOURS: true — keep answering and taking orders`, and the processor sends the workspace system message `out_of_hours[lang]` as a standalone message before the AI reply, once per conversation per 24 h (`context.systemMessageSentAt.out_of_hours`).
3. **Custom instructions** — `Agent.customInstructions` (≤ 10 000) under `OWNER INSTRUCTIONS` (they override the personality and every style habit; the OUTPUT section ends with a check against them — tester report 2026-10-20).
4. **FAQ** — `AgentFaq` entries (≤ 50, total ≤ 20 000 chars) as `Q: … / A: …`.
5. **Catalogue** (D34): if `scope.count ≤ 60` ⇒ full list, one product per block:
   ```
   #{n} {name} [ID:{id}] SKU:{sku} PRICE:{price} DA{oldPrice? ' (was {oldPrice} DA)'} STOCK:{'in stock'|'out of stock'|'out of stock (orderable)'|'service'}
   {description ≤ 300 chars}
   VARIANTS: {name} [VID:{id}] {price} DA stock {stock}; …
   ALSO: {recommendedName} [ID:{id}] {price} DA — {reason}
   ```
   else ⇒ `CATALOGUE: {count} products. Use search_products before naming any product.` + the last-mentioned products (`context.lastProductIds`, full blocks) + products matched by trigram on the current batch text (top 30 via `ProductSearch.search(workspaceId, agentScope, text, 30)`).
   Scope = `AgentProduct` rows when `sellAllProducts=false`, else `Agent.catalogScope='categories'` ⇒ products in `scopeCategoryIds`, else all; always filtered `isActive && deletedAt IS NULL && moderationStatus IN ('approved','not_required')` (AI-14, D36), or `pending` with an approved snapshot — then its approved name, description, price, pictures and variants only (04 §12; the `ALSO` lines too). Rule line `NOT_LISTED` (tester log 26/10 UX-038): a product or variant that is not in the list (full catalogue) or not returned by `search_products` / `get_product` is not available, even when the customer names it or an earlier message mentioned it — say so, never confirm, show or order it. Out-of-stock handling: the workspace system message `out_of_stock[lang]` is injected verbatim as `OUT_OF_STOCK_SENTENCE: "{systemMessages.out_of_stock[lang]}"` (the `{product}` placeholder is kept; the model fills it with the product name) and `Agent.outOfStockBehavior` adds `suggest_alternative` ⇒ `OUT_OF_STOCK: say OUT_OF_STOCK_SENTENCE, then suggest an alternative from the same category`; `say_unavailable` ⇒ `OUT_OF_STOCK: say OUT_OF_STOCK_SENTENCE only`; `Agent.showMissingVariants` ⇒ `MISSING_VARIANT: say which sizes remain`. **Stock is private** (recette 09/11): the prompt and the `search_products` / `get_product` results carry no stock count, only `in stock` / `out of stock` (per variant too), and the rule line `STOCK_PRIVATE` forbids telling a customer how many units are left; the only number the model ever gets is `available` in an `ORDER_INSUFFICIENT_STOCK` result, when the customer asked for more.
6. **Delivery** — `DELIVERY FEES: use quote_delivery. Free delivery from {freeDeliveryThreshold} DA.` + sender wilaya.
7. **Order-taking rules** (agent behaviour step 3, fields from `Agent.orderFields` JSON): required fields in order `product+variant → quantity → name → phone (10 digits, 05/06/07) → wilaya → commune → address or stop-desk`; optional `secondPhone`, `note`; `MAX_QTY_PER_ORDER={agent.maxQtyPerOrder}`, `MAX_AMOUNT={agent.maxAmountPerOrder} DA` ⇒ above ⇒ handoff (a null limit is no limit and its line is left out; none set ⇒ "never refuse or hand off an order because of its size", PV 28/10); `RISKY_CLIENT_POLICY={agent.riskyClientBehavior ?? 'take_and_flag'}`; `RECAP={agent.recapMode ?? 'always'}`; "ask one field at a time; never invent; re-ask invalid values with an example (0555123456)"; duplicate rule; cancel rule (`cancel_order` only, never create).
8. **Image rule** (when `imageRecognition`): `IMAGE RESULT: {vision pass-2 result}` injected as a system note per image: `{productId, confidence}` or `unsure` or `multiple` or `blurry` + the behaviour: `< 0.7 ⇒ ask the customer for confirmation; never state a price for an unconfirmed match`.
9. **Cross-sell** — `Suggest at most 1 complementary product per conversation, only from ALSO lines, only after the customer chose a product.` (M11: dedicated section "CROSS-SELL (RECOMMENDATIONS)" with the source → recommended pairs of the catalogue, ≤ 30 lines, and the REC-01 hard cap of 3 suggestions per reply in `recommendations`.)
10. **Product card template** — `When presenting a product use this template: {productCardTemplate}` (placeholders `{name} {price} {description} {stock}`) else default `{name} — {price} DA`.
11. **Closing instructions** — `Agent.closingInstructions`.
12. **Handoff rules** — built-ins (customer asks for a human / refund / complaint; angry tone; 3 unclear in a row; off-catalogue question; order above limits; blocked/risky client policy; custom keywords `agent.handoffKeywords[]`) + `Agent.humanHandoffRules` free text. Instruction: `status=HANDOFF with statusDetail=<rule id>`.
13. **Language rule (strict)** — AI-01 text: same language and script as the last customer message (Arabic-script darija, Latin arabizi with 3/7/9, French, English, mixed); never switch; product names/SKUs/prices verbatim with Latin digits and "DA" (Arabic script replies use "دج").
14. **Output contract** — the JSON schema of §4.1 is passed as `experimental_output: Output.object({ schema })`; the system text ends with `Return only the structured output.`

Messages: last 30 `Message` rows of the conversation (customer ⇒ `user`, ai/human ⇒ `assistant` with prefix `[human: {name}]` for human replies, system events skipped), audio replaced by `[voice note transcript]: …`, images replaced by `[image]` + the vision note; the current batch's messages are concatenated into the final `user` message separated by newlines. **New visit** (recette 09/11): a customer message more than 6 h after the previous message of the thread (Messenger keeps one thread per customer) starts with the note `[NEW VISIT: …]` — the model answers it for itself and does not resume the earlier product, order or question unless the customer refers to it (`NEW_VISIT_AFTER_MS`).

Token budget: `AiModel.contextTokens − maxTokens − 512`; if exceeded, drop oldest history messages first, then truncate FAQ, then catalogue descriptions to 100 chars.

### 3.6 Language detection
`detectLanguage(text)`: Arabic script ratio > 0.4 ⇒ `ar`; Latin text with ≥ 2 arabizi markers (`3`, `7`, `9`, `kh`, `ch`, `wach`, `rani`, `bghit`, `kayen`) ⇒ `arabizi`; French stop-words ⇒ `fr`; else `en`; mixed scripts ⇒ `mixed`. Stored in `context.lastLanguage`; used to pick system messages (`ar` for `ar`, `fr` for `fr|mixed`, `en` for `en`; journey retest R2-5 (17/11): `arabizi` has no text of its own — it takes the Arabic text when the shop speaks darija (`Agent.defaultLanguage` `darija` / `ar` / `arabizi`, or, with no default or kabyle, a workspace in Arabic) and the French one otherwise; `systemLocale(lang, workspaceLocale, agentDefault)`, `systemLang` for the welcome / out-of-hours / handoff texts of a live AI turn; a handoff text sent by the messaging module itself still reads the workspace locale only). Journey retest R4-2 (17/11): inside a conversation, Arabic-script words that are only a value — a name typed in Arabic script (« سمير بن علي », « smiti وليد بوزيد »), a place or an address — say nothing of the language (`arabicValuesOnly`: at most 4 such words besides address words, none of them a greeting / thanks / yes-no / « اسمي » / question / darija / MSA word; « عبد السلام » is a name): the Latin rest decides, else the conversation keeps its language (the French customer of N4 and the arabizi one of F3 got every later reply, the recap and the confirmation in Arabic script); the reply guard reads the current message the same way (`withoutArabicValues`), so an Arabic reply to that name is a `language_switch`. Each turn is read with the conversation's language before it (`turnLanguage` / `conversationLanguage`, language.ts — live reply and playground alike; journey 16/11 J05-8): a text with no clue (a phone number, a name, « ok ») keeps that language whatever it is, Arabic script included; only the first message of a conversation with no clue falls back on **the shop's language** (journey 16/11 J04-2, `shopLanguage`: the agent's default language — `fr` / `en` / `arabizi` as is, `darija` / `ar` ⇒ `arabizi` for Latin letters and `ar` for a text with no letter; kabyle or none ⇒ the workspace language), no longer English for any Latin text. The playground reads its earlier customer turns in order, each with the one before (a bare « Nadia Ferhat » read alone gave English, and the phone number after it was answered in English). Journey 16/11 J04-2: « Bonsoir », « bsr », « bjr », « slt » are French words; address and place words (« cité », « logements », « bloc », « villa », « numéro », « wilaya », « Sétif », « Médéa »…) count for no language; inside a conversation a Latin message switches the language only with **2 clues or more** (one « oui », « merci », « thanks » keeps it; « Bonjour, et pour Blida ? » or « And to Annaba? » switches it; a change of script always switches). The welcome and out-of-hours texts of the live reply take the language of the turn (`sendSystemText(…, { lang })`), as the playground's. An Arabic-script message in formal Arabic (MSA markers « هل », « ما هي », « يمكنني », « كم », « إلى »… and no darija word) sets `PromptContext.formalArabic`: DETECTED_LANGUAGE then reads « formal Arabic (MSA) — answer in simple formal Arabic, not in darija » (J04-3 P08). Journey retest R1-3 (17/11): in an arabizi conversation a message with one darija word stays arabizi whatever French nouns it carries (« nheb nechri 2 tapis de prière » was read as French — « de », « prière » — and every reply from the phone on, recap and confirmation included, came in French); more darija markers (nechri, zoudj / jouj, wahed / wahda, tlata, smiti / smitek, goulili, rahi, wla, lkamla, dork, bessah, ghir, bach…); the language section asks for whole darija sentences after a phone / name / address message and for fee answers (examples), and the server recap / confirmation take the turn's language. Journey retest R3-1 (17/11): « khouya twasslou l Constantine ? ana f El Khroub, cité 1000 logements bloc 5 » after two French messages stayed French (one clue: the « kh » of « khouya »; « El Khroub » counted as darija too), so the server recap came in French and the confirmation of the next « ih saha » in arabizi. More markers (khouya, ana, ntouma, twasslou / nwasslou / ywasel, t7ebb…), the one-letter prepositions « l », « f », « fi » count half a clue each, place names with « kh » / « ch » (El Khroub, Khenchela, Khemis, Ksar El Boukhari, Chlef, Cherchell, Chelghoum…) count for no language, and a typographic apostrophe is read as a straight one (« l’adresse » is one word). A clear switch (2 clues or more) moves the conversation language for that turn and the next ones — the server recap of the switch turn and the confirmation of the next turn are built in the same language (`turnLanguage` / `conversationLanguage`); one darija word in a French message (« merci khouya ») still keeps French.

## 4. Structured output & tools

### 4.1 Output schema (`AiReplyOutput`, zod → JSON Schema)
```json
{ "type": "object", "additionalProperties": false, "required": ["reply", "status", "intent", "productCards", "recommendations", "confidence"],
  "properties": {
    "reply": { "type": "string", "maxLength": 2000 },
    "status": { "enum": ["OK", "UNCLEAR", "UNKNOWN", "HANDOFF"] },
    "statusDetail": { "type": "string", "maxLength": 200 },
    "evidence": { "type": "string", "maxLength": 300, "description": "status=HANDOFF only: the customer's exact words, from their current message, that match the handoff rule" },
    "intent": { "enum": ["SALE", "INFO", "TRACKING", "COMPLAINT", "GREETING", "OTHER"] },
    "productCards": { "type": "array", "maxItems": 5, "items": { "type": "string", "description": "productId" } },
    "recommendations": { "type": "array", "maxItems": 3, "items": { "type": "object", "required": ["sourceId", "recommendedId"], "properties": { "sourceId": { "type": "string" }, "recommendedId": { "type": "string" } } } },
    "confidence": { "type": "number", "minimum": 0, "maximum": 1 },
    "language": { "enum": ["ar", "arabizi", "fr", "en", "mixed"] },
    "customer": { "type": "object", "description": "order details the customer has given so far" },
    "cart": { "type": "object", "properties": { "items": { "type": "array", "maxItems": 20, "items": { "required": ["productId"], "properties": { "productId": {}, "variantId": {}, "quantity": {} } } } }, "description": "full-test 15/11: the product(s) chosen for the order being taken (§2 `chosen`)" }
  } }
```
Malformed ⇒ one retry with the model's answer as `assistant` + a `user` message `Format reminder: answer with the one JSON object of the OUTPUT section only (your answer above goes in "reply", with the same meaning — do not correct it, do not mention this reminder), no text around it.`; that retry keeps only the last 8 messages of the conversation (+ the batch, this turn's tool calls / results and the answer — in a long thread the model otherwise copies the plain-text style of its past replies, tester report 22/10; with none of them it concluded it had invented the customer's details and cancelled the order, full-test 15/11 AI-CHAT-02) and offers **no tool**; still malformed ⇒ the first answer is sent when it is a plain message to the customer (no JSON object) or an object whose `reply` string is complete, with status `OK`, intent `OTHER`, confidence 0.5 and the run flag `format_salvaged`; F-6 only when nothing can be sent (tester report 26/10). An object right in substance but not to the letter is not malformed: unknown keys are dropped, `status` / `intent` / `language` are read case-insensitively (unknown ⇒ `OK` / `OTHER` / absent), `confidence` given as text or as a percentage is read, `productCards` / `recommendations` / `reply` / `statusDetail` / `customer` fields are cut to their maximum; only a missing or non-text `reply` is malformed.

### 4.2 Tool schemas (`ToolRegistry`; names are final; `maxSteps = 4` = 3 tool rounds + final answer)

Tool result codes (`PRODUCT_NOT_AVAILABLE`, `ORDER_NOT_CANCELLABLE`, `NO_OPEN_ORDER`, `WILAYA_NOT_SERVED`, `VARIANT_REQUIRED`, `ORDER_INSUFFICIENT_STOCK`, `CUSTOMER_BLOCKED`, hint `order_limit`) are internal to the AI run, never returned by the API, not in 11.

Validation inside every tool uses `packages/shared` validators; a validation failure returns `{ ok:false, error:{ code, field, example } }` to the model (never throws), so the model re-asks.

### 4.3 Reply guard and rule coverage

Weak-points audit 12/11, pattern 1 (owner go-ahead 14/11): about fifty « never / always / only » sentences of the prompt were held by the model alone. The **reply guard** (`modules/ai/reply-guard.ts`, pure, unit-tested in fr / ar / darija / arabizi / en, positive and negative cases) checks the reply TEXT before it is stored or sent — in `AiRunService.turn`, so the live reply job (`reply.processor.ts`, between the model loop and `finalize`) and the playground (`playground.service.ts`, and therefore the 8 wizard scenarios and the eval runner) behave the same.

**Facts** (`guardFactsOf(prompt, …)` → `GuardFacts`, + `withToolResults` for every tool result of the turn as it comes):
- prices: catalogue products without variants (+ old price and the discount old − new), every variant price (never the base price of a product sold by variant), ALSO lines, every `price` / `unitPrice` / `oldPrice` of a tool result;
- amounts: every number of a tool result of this turn **and of the earlier turns of the conversation** (last 40 executed `AiToolCall`s of its runs; playground: of the session) except ids and stock counts; every number ≥ 10 of the texts the shop wrote (policies, FAQ, owner / closing instructions, card template, handoff rules, system messages, product descriptions); every number ≥ 50 the customer wrote in the message(s) answered (the AI may repeat « 3500 DA » to refuse it); the free-delivery threshold;
- fees: `fee` / `stopdeskFee` / `deliveryFee` of tool results + the shop-text numbers; thresholds: `freeFrom`, `freeDeliveryThreshold`;
- stock counts: `available` / `availableAllVariants` of a tool result (ORDER_INSUFFICIENT_STOCK) — the only counts the reply may state;
- tokens (never a « code »): SKUs, product / variant names, order / tracking numbers, wilaya and courier names of tool results, CAPS_CODES the shop wrote (a promo code);
- the agent name the prompt gives the AI (`approvedDisplayName`, else `approvedName`, moderated since 11/11; none ⇒ no personal name), the shop name;
- `answeredBefore` (an AI or team message in the history), `freshStart` (the history's NEW_VISIT / RESUMED: the batch opens a new visit, or is the first message after the team gave the thread back), `customerGreets` (the batch starts with a greeting).

Only the corrective answer's `reply` text is taken: status, statusDetail, cards, photos, recommendations, `customer` and every tool effect stay the first answer's — the guard never changes a handoff and **never hands off**. The corrective turn is asked only when a model step is left and ≥ `GUARD_RETRY_MIN_MS` (8 s) of the 45 s budget remains; after a format retry (§4.1 salvage) it is skipped. The corrective answer still breaks a rule (or is empty / malformed, or the call fails / runs out of time) ⇒ **enforcement** (`enforceReply`): the sentences holding an `unknown_amount`, `stock_count`, `technical_leak`, `self_name`, `false_confession` or `contradicts_customer` are dropped and an opening greeting is stripped (`repeat_greeting`, with its companions « Bonjour Madame, », « Salam khouya, »); what remains is sent when it has ≥ 2 words; else one neutral sentence of the customer's language (`SAFE_SENTENCES`, fr / ar / arabizi / en, never a promise that the team will answer): a wrong amount with product cards ⇒ « Le prix est indiqué sur la fiche du produit ci-dessous. »; only a stock count ⇒ « Oui, ce produit est disponible. »; otherwise ⇒ « Pouvez-vous me préciser le produit (taille ou couleur) et, pour la livraison, votre wilaya ? »; only a wrong name ⇒ « Je suis {approved name}, l'assistant virtuel de la boutique. » (no name ⇒ « Je suis l'assistant virtuel de la boutique. »); only a repeated greeting with nothing after it ⇒ the reply is sent as it is (`kept`). Blocked words (§11) are checked after the guard, on the text that will be sent.

**Recorded** on the run: `AiRun.meta.guard = { violations: [{ rule, value?, kind? }], retried, remaining: [...], action: rewritten | stripped | safe_sentence | kept }` (rules, amounts / counts and leak kinds only — never message text) and `AiRun.flags += guard_rewritten | guard_enforced | guard_kept`; the playground's test runs carry the same meta (the DTO is unchanged: the reply shown is the guarded one). `tools/deploy/diag-conversation.cjs` shows a « guard » column per run of a conversation and, in the 24 h overview, the guarded runs by action and rule and the last 15 guarded replies (time · shop · conversation · `unknown_amount=3900 → ok` · action).

**Credits** (§7): the corrective turn is part of the same run and the same reply: no extra credit (a text reply costs 1 credit whatever the number of model calls, like the format retry and the handoff re-ask); its tokens are added to `AiRun.inputTokens` / `outputTokens` and to `costUsd`.

## 5. Idempotent run (`AiRunService`, 04 §5)

```
start(batchKey):  AiRun upsert on (conversationId, batchKey) [columns `AiRun.batchKey`, unique with `conversationId`; `AiRun.flags[]`, `AiRun.meta` = §13 metrics] → if exists && status='running' reuse (replay) else create { status:'running', attempt }
loop:             for each model tool call with callId:
                    AiToolCall find (aiRunId, callId) → if result exists → return stored result (no execution)
                    else insert { callId, name, args, executedAt:null } → execute → update { result, executedAt }
welcome:          first AI reply of a conversation created in this run's batch (no earlier Message with author ∈ ai|human) ⇒ Message(author:'system', payload.system.kind='welcome') with Workspace.systemMessages.welcome[lang] ({shop} = workspace.name) enqueued BEFORE the reply; empty string ⇒ skipped; context.systemMessageSentAt.welcome set
send:             Message(author:'ai', aiRunId) created BEFORE enqueueing meta-send; outbox key send:<messageId>; cards as separate messages payload.cards
finish:           AiRun { status: ok|unclear|unknown|handoff, inputTokens, outputTokens, latencyMs, confidence, modelId, finishedAt }
```
`callId` = `sha256(name + canonicalJson(args))` + its ordinal among identical calls of the run (provider tool-call ids change when the model is re-prompted on a retry, so they are never the persisted key). A replayed `create_order` therefore returns the already-created order (AT-AI-05). Runs older than 5 min in `running` are reaped (`sched-ai-run-reaper`) with credits released; a reaped run is not resumed (the next customer message starts a new batch).

## 6. Provider routing & fallback

`AiRoute(capability ∈ text|vision|transcription|embeddings, primaryModelId, fallbackModelId, creditCost, timeoutSec=20, errorThresholdPct=2, failoverActive, failoverSince)` edited on ADM-06; window for the error rate is fixed at 10 min; `timeoutSec` applies per model call (the 45 s figure below is the whole-run budget).

- Agent model = `Agent.modelId`, assigned by the platform routing (R-H): at every agent save `Agent.modelId = AiRoute(capability='text').primaryModelId` (or `fallbackModelId` while `failoverActive=true`); at run time, if `Agent.modelId` is not `AiModel.isActive && supportsTools` or the circuit breaker is open, the run uses the route's other model and writes it back to `Agent.modelId`. The merchant never chooses a model; the UI shows a read-only model badge; `temperature` / `maxTokens` come from the agent's preset (`AgentPreset`) and are not editable by the merchant.
- Vision capability = model with `supportsVision`; voice = Groq `whisper-large-v3-turbo` primary, OpenAI `whisper-1` fallback (fixed, not in `AiRoute` UI except timeout); embeddings = P3 (`embeddings_retrieval` flag; `text-embedding-3-small`; off by default).
- Failure classes: `provider_error` (5xx, network, 429 after SDK retry 2×, timeout 45 s) ⇒ one retry on the fallback model within the same attempt; `provider_rejected` (401/403) ⇒ `AI_PROVIDER_KEY_REJECTED` platform alert, fallback immediately; `content/format` ⇒ format retry (§4.1) then F-6.
- Circuit breaker per model: Redis window counters; error rate over `errorRateThresholdPct` in `windowMin` ⇒ route to fallback for 5 min (ADM-01 alert "bascule Anthropic active"); half-open after. Journey retest R1-1 (17/11: « ai circuit breaker opened » with `errors: 2, total: 15` at a 2 % threshold): the rate is read only from `BREAKER_MIN_CALLS = 20` calls and `BREAKER_MIN_ERRORS = 5` failures in the window (`breakerTrips`); a failure of this process (`AiProviderError.local`: the SDK refused the request or could not read the step) never counts.
- Cost: `AiRun.costUsd = inputTokens × inputPricePerM/1e6 + outputTokens × outputPricePerM/1e6` computed at finish (ANA-02 consumption, ADM-01).
- **Provider compatibility** (live, 2026-10-14, `LiveAiGateway`): (a) the SDK always sends a `temperature`; a model that answers 400 "`temperature` is deprecated for this model" (Claude 5.x) is asked again without it, and its `provider:modelId` is remembered in the process so later calls omit it at once (one request per reply, not two; the memory is per process and resets on restart); (b) tool input schemas never use `anyOf` / `oneOf` / `allOf` at the top level (Anthropic answers 400 "input_schema does not support oneOf, allOf, or anyOf at the top level"); required-one-of rules are checked by the handler (`INVALID_ARGS`), and a unit test (`tool-registry.spec.ts`) keeps every tool schema provider-safe; (c) a failed call logs the provider's error type and the parameters it cites, never its free text (PII). (d) a model step offered no tools (the last step of the loop, or the step after a `handoff_to_human` call / a forced handoff) carries the earlier tool calls and results as plain text (`[tool call name {args}]` / `[tool result name] {json}`): Anthropic answers 400 to `tool_use` / `tool_result` blocks in a request without tool definitions, which ended the conversation with the « IA indisponible » banner right after a handoff tool call (tester report 26/10); (e) `AiRun.error` of a provider failure is `<class>:<status> <error type>` (e.g. `provider_error:529 overloaded_error`), never the provider's text; journey retest R1-1: never a bare class either — no HTTP answer ⇒ `provider_error:network`; an SDK error that is not an HTTP answer ⇒ `provider_error:sdk:<name>` (`sdk:no_such_tool`, `sdk:invalid_tool_args`, `sdk:invalid_prompt`, `sdk:unsupported`, `sdk:response_parse`…, the SDK error's name only) with `local = true`. (f) Prompt caching (proposal 13): one `cache_control` breakpoint (of the 4 allowed) on the system block of the stable prefix (identity → catalogue); a prefix under ~3 500 characters is sent without it (a prefix below the model's minimum only fails to cache, it is never refused); the tools render before the system prompt, so a turn that withholds `handoff_to_human` (field-only) re-reads the prefix uncached — accepted; the note of such a turn goes after the prefix. Live routes: text + vision on `claude-haiku-5-5`, fallback `claude-haiku-4-5` (07 §12).

## 9. Vision (AI-06) and voice (AI-07)

## 10. Handoff & insights (AI-08, FL-03)

**Handoff check by the server** (`handoff-judge.ts`, retest 12/11 « transfers for no reason, even after a hello; once confused it keeps doing it »), on both ways the model can hand off — the `handoff_to_human` tool (new required argument `evidence`) and `status = HANDOFF` in its answer (`evidence` field): reasons the server sets itself (`order_limits`, `risky_client`, `blocked_word`, `orders_unavailable`, tool hints) pass only when a tool result of the same turn established them (journey retest R4-1, 17/11: `establishedReasons` — `create_order` `hint: order_limit` ⇒ `order_limits`, `CUSTOMER_BLOCKED` / `hint: risky_client` ⇒ `risky_client`, `ORDERS_UNAVAILABLE` ⇒ `orders_unavailable`; `handoff_to_human { order_limits, evidence « placeholder » }` had been accepted on « Je voudrais le sac à main cuir marron » and on an address; otherwise `why = server_reason`), and they are never offered in the tool's `reason` enum (`allowedHandoffReasons`: customer_request, refund, complaint, angry, off_catalogue, keyword with keywords, other with « Shop rules », unclear_streak on the 3rd); a handoff answer never claims a recap that was not shown (`withoutRecapClaims` drops « récapitulée ci-dessus », « Répondez oui… » from it); `unclear_streak` only on the 3rd unclear message in a row; `keyword` only when a handoff keyword is in the current message; `other` only with « Shop rules »; `customer_request`, `refund`, `complaint`, `angry`, `off_catalogue`, `other` need `evidence` = the customer's words found in the message(s) being answered (whole quote, or ≥ 2 of its words and 60 %), never a greeting-only message. Journey 16/11 J04-5 (`reasonFits`): the words must also fit the reason — `customer_request` needs words asking for a person or a call (« humain », « conseiller », « parler », « someone », « bnadem », « نهدر »…) or a cancellation / change the AI cannot make (« annuler », « modifier »…), and never a question about the assistant alone (« are you a real person? », « t'es un robot ? » without « parler / talk… »); `refund` needs words asking for money back; `off_catalogue` is never a discount / price / free delivery « the owner said » (« Le patron a dit -50 % ») unless the customer asks for wholesale, a custom order or a partnership; `off_catalogue` and `complaint` are never a question about the assistant (« what is your name? »). Refused ⇒ `why = reason_mismatch` (the instruction says: answer with the catalogue price / say you are the shop's virtual assistant). `angry` and `other` stay the model's judgement. Refused tool ⇒ `HANDOFF_NOT_NEEDED { why }` + instruction, the model answers in the same turn; refused `status = HANDOFF` ⇒ the model is asked once more with the reason (`HANDOFF REFUSED BY THE PLATFORM: …`), and when it insists its reply is sent with status OK (the AI keeps the thread) — only an empty reply lets the handoff through. `AiRun.flags += handoff_refused`; `diag-conversation.cjs` counts them. One message, not two (recette 09/11): when the reason is `customer_request` or `keyword`, no tool other than `handoff_to_human` ran in the turn (the reply carries no order or cancellation news) and the shop's `handoff` text is about to be sent (first of the episode, non-empty), the model's own reply is dropped — the shop's text is the only message; for the other reasons the reply is kept (it answers what else was asked). ## 12. 24 h window rules applied to AI sends (MSG-06)

`WindowRules.canSend(channel, conversation, kind)`:
- `kind='ai'`: FB and IG — only if `lastCustomerMessageAt ≥ now − 24 h`; otherwise the run is aborted before generation (credits released) and the conversation gets `needs_human` with insight detail `outside_window`. AI never uses message tags.
- `kind='human'`: FB inside 24 h ⇒ standard; FB outside ⇒ `messaging_type=MESSAGE_TAG, tag=HUMAN_AGENT` (one attempt; Meta refusal ⇒ 422 `REPLY_OUTSIDE_WINDOW`); IG outside ⇒ 422 `REPLY_OUTSIDE_WINDOW` without attempting.
- `kind='transactional'` (order/shipment/payment system messages): FB and IG inside 24 h ⇒ standard, outside ⇒ `Message.deliveryStatus='skipped_window'` (thread label) — Meta retired `POST_PURCHASE_UPDATE` on 2026-04-27 (#100, Messenger changelog 2026-03-27).
- `kind='system'` (workspace system messages `handoff`, `out_of_hours`, `out_of_stock`, `welcome` + fixed platform texts `unavailable`, `unsupportedMedia`, `voiceFailed`): same as `ai` (inside window only; they are always replies to a fresh customer message so this holds). `out_of_stock` is never sent on its own: it is the sentence the AI reply contains (§3.5).

## 16. Do / Don't

**Do**
- Persist `AiToolCall` before executing a tool; return the stored result on replay.
- Reserve credits at job start and settle only on the conditions of §7.
- Filter the catalogue with `isActive && deletedAt IS NULL && moderationStatus IN ('approved','not_required')` in every tool and prompt section.
- Validate every tool argument with the shared validators and return `{ ok:false, error }` to the model.
- Send the text reply first, then ≤ 5 cards, each as its own outbox send keyed by message id.
- Pass the turn's `GuardFacts` (§4.3) to `AiRunService.turn` in every path that answers a customer (reply job, playground): a new prompt rule that can be checked on the text gets a guard rule or a row « prompt only — why » in the §4.3 table.

**Don't**
- Don't let the model set prices, fees or stock; all numbers come from tool results (the reply guard, §4.3, checks every amount and stock count of the text).
- Don't let the reply guard hand off, change the status / cards of the answer or call a tool: it only rewrites or trims the text.
- Don't call `create_order` without `customerConfirmed:true`; don't create an order from `cancel_order`.
- Don't use Meta message tags for AI sends.
- Don't send the handoff message twice in 24 h for the same conversation.
- Don't charge credits on provider errors, malformed output, reaped runs or playground turns.
- Don't include non-approved, archived or out-of-scope products in prompts, cards or search results.
